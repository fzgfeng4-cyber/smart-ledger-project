# Smart Ledger V1 用户体验与页面方案

## 文档定位

- 状态：V1 UX/UI 正式方案，主 Agent 最终决策检查点已通过，供 Frontend Agent、Backend Agent、Test Agent 和 Review Agent 读取。
- 范围：只定义用户看到什么、页面如何组织、状态如何表达、用户如何操作；不定义 Vue、FastAPI、数据库或业务实现代码。
- 依据：`PROJECT.md`、`docs/product-v1.md`、`docs/data-model.md`、`docs/classification-rules.md` 和 `skills/ui-design.md`。
- 目标：让个人用户每天用最少的步骤完成“一句话输入 -> 检查或修改 -> 确认记账”，同时把规则识别的不确定性明确交给用户。
- V1 原则：识别结果永远是建议，只有用户明确确认后才成为正式账目。

## 1. 总体结论

### 1.1 页面数量

V1 使用 **3 个主页面**，不建立独立设置页，也不建立独立详情页：

| 页面 | 作用 | 进入方式 |
| --- | --- | --- |
| 首页 | 查看三个基础统计、快速记账、回看最近账目 | 应用打开后的默认页 |
| 账单列表 | 按日期查看全部有效账目 | 首页“查看全部”或顶部导航 |
| 账目工作页 | 新增账目的输入/确认状态，以及已保存账目的查看/编辑状态 | 首页快速记账、列表行或“记一笔” |

“快速输入”“解析确认”“重复提醒”“删除确认”“删除后撤销”都是页面状态、轻量提示或小型确认层，不额外计为页面。新增和编辑复用同一个账目工作页，减少跳转和两套表单的差异。

### 1.2 不设置页的处理

V1 没有账号、主题、分类管理、同步或复杂偏好，因此不需要设置页。首页右上角的“更多”菜单只放一个入口：

- `备份数据`：点击后下载本地 SQLite 备份文件；页面只负责入口、进度或成功/失败提示，不设计恢复中心和技术细节。

### 1.3 最短正常路径

1. 打开首页，快速输入框自动获得焦点。
2. 输入“35块买菜”，按 Enter，或点击“识别”。
3. 账目工作页展示 `¥35.00 / 支出 / 买菜/食品 / 买菜 / 今天`，用户可检查五个业务字段。
4. 点击一次“确认记账”。
5. 回到来源页并显示“已记账”，首页统计和最近账目立即更新。

## 2. 设计原则

1. **快**：首页打开就能输入；Enter 和移动端键盘动作都能开始解析；常规确认不要求填写复杂表单。
2. **少点击**：正常识别只需一次解析和一次确认；分类冲突提供同屏一键切换；编辑沿用同一套字段。
3. **看得懂**：用户只看到“收入、支出、餐饮、买菜/食品”等中文标签，不看到 `expense`、`groceries_food`、`deleted_at` 等内部值。
4. **不替用户做危险猜测**：金额、方向、分类、日期存在关键缺失或冲突时，明确标记并禁用保存。
5. **容易修改**：确认页直接改金额、收入/支出、分类、备注和日期；需要改整句话时原句保留并可返回输入框。
6. **轻量反馈**：使用短提示、状态标签和必要图标；不使用炫酷动画、复杂图表、聊天界面或企业后台式仪表盘。
7. **信息不过载**：列表只显示金额、收支、分类、备注、日期；原始输入仅在确认和编辑/查看时展示。

## 3. 页面框架与视觉基线

### 3.1 导航

- 顶部左侧显示 `Smart Ledger`，旁边只有“首页”和“账单”两个导航项。
- 顶部右侧使用一个有明确文字标签或可访问名称的“更多”按钮，菜单项为“备份数据”。
- 首页和账单列表都提供“记一笔”入口；首页优先显示输入框，列表页使用按钮进入账目工作页。
- 不显示登录入口、账户头像、同步状态、通知中心或设置中心入口。

### 3.2 页面宽度和控件尺寸

- 桌面端使用居中的窄内容区：首页和列表适合扫描，账目工作页控制在单栏阅读宽度，避免企业后台多栏布局。
- 手机端使用单栏全宽布局，左右保留稳定内边距，不出现横向滚动。
- 快速输入框桌面端高度约 52 至 56 像素，手机端不低于 52 像素；输入与“识别”按钮都要容易点击。
- 普通按钮、分类选项和列表操作的可点击区域不低于 44 像素；保存按钮在手机端固定在底部可见区域，并为正文预留底部空间。
- 状态提示使用短标签加文字说明，不依赖颜色单独传达含义。颜色只作为辅助：注意使用琥珀色，错误/删除使用红色，成功使用绿色，收入和支出可用不同强调色，但始终保留“收入/支出”文字。
- 图标只辅助编辑、删除、备份、返回等动作；图标按钮有清晰的文字名称或悬浮说明，不用陌生图标代替关键文字。
- 不使用复杂动画。解析中只需要轻量的“正在识别”状态，不让布局跳动。

### 3.3 用户字段显示映射

| 数据概念 | 用户看到的内容 | 交互规则 |
| --- | --- | --- |
| `amount_cents` | `¥35.00`、`¥8,000.00` | 页面输入和展示使用元；支出不显示成负数，收支由文字标签区分。 |
| `type` | `支出` 或 `收入` | 使用二选一控件；未选择时显示“待选择”。 |
| `category` | 中文分类名 | 从固定 V1 分类选择；不展示内部 code，不允许临时创建分类。 |
| `note` | 用户备注；为空时显示“未填写” | 可填写、修改或清空；“未填写”只是界面提示，不写入数据库。 |
| `original_text` | “原始输入：35块买菜” | 确认页和编辑/查看页只读展示，不作为列表核心内容。 |
| `transaction_date` | “今天 · 2026年8月30日”等本地日期 | 可改为有效的今天或历史日期；未来日期默认禁止保存。 |

## 4. 首页方案

首页固定按以下层级排列：**顶部统计 -> 快速记账 -> 最近账目**。统计区域保持紧凑，不抢占输入区域。

### 4.1 顶部统计

只显示三个统计项：

1. 今天支出
2. 本月支出
3. 本月收入

金额展示为人民币格式，例如 `¥35.00`。统计只包含已保存且未软删除的账目；待确认草稿、已删除账目不计入统计。没有数据时显示 `¥0.00`。数据读取失败时不要伪装成零，显示“暂不可用”并提供“重试”。

不显示余额、收支相减结果、预算、趋势图、分类占比、年度报告、消费建议或账户信息。

### 4.2 快速记账

- 区域标题：`快速记账`。
- 输入框 placeholder：`例如：35块买菜`。
- 输入框支持一行自然语言；输入内容较长时允许换行或保持可横向编辑，但不主动截断。
- 桌面端按 Enter 解析；手机端键盘的完成/前往动作也触发解析；同时保留明确的“识别”按钮，方便触屏用户操作。
- 输入框在首页打开时优先获得焦点，但不打断用户从其他页面返回时正在阅读的内容。
- 解析期间按钮变为“识别中”，输入内容保持可见；不要重复提交同一请求。
- 空输入时不进入确认页，只在输入框下方提示“请输入一笔账，例如：35块买菜”。
- 解析失败或字段缺失时绝不清空输入；用户可继续改写原句或在确认状态直接补字段。

### 4.3 最近账目

- 默认展示最近 5 笔有效账目，按账务日期从新到旧，同一天内按最近保存/修改顺序排列。
- 每行显示：金额、收入/支出、分类、备注、日期。
- 支出示例：`支出  ¥35.00  买菜/食品  买菜  今天`。
- 收入示例：`收入  ¥8,000.00  工资  工资  今天`。
- 没有备注时显示“未填写”，不写“无备注”。
- 点击一行进入账目工作页的编辑状态；“查看全部”进入账单列表。
- 删除等操作在编辑状态完成，不在首页行内放大量操作按钮。

### 4.4 首页空状态

统计仍显示三个 `¥0.00`。最近账目区域显示：

> 还没有账目
> 
> 输入第一笔，例如“35块买菜”。

快速记账输入框保持可用，不增加引导页、插图或营销文案。

## 5. 快速输入与解析状态

### 5.1 输入控件

- 使用单个主输入框承接一句话，不拆成金额框和事项框，避免用户先思考字段。
- 输入框必须允许中文、数字、常见金额单位和日期表达。
- 用户按 Enter 或点击“识别”后，进入账目工作页的解析确认状态；解析器不能直接保存。
- 输入为空时停留在首页输入状态。
- 用户返回修改原句时，原文完整回填输入框，保留用户文字顺序、空格和标点；用户可直接编辑后再次识别。

### 5.2 解析状态的用户表达

后端/解析器的 `ready`、`needs_confirmation`、`needs_input`、`no_draft` 只作为前端状态依据，用户界面使用以下中文标签：

| 用户标签 | 含义 | 展示方式 |
| --- | --- | --- |
| `已识别` | 字段已有合法建议，用户仍需在确认页检查 | 字段右侧小标签或低调图标。 |
| `待确认` | 有候选值，但需要用户明确保留或改选 | 琥珀色辅助标签，下面给出一句原因和直接操作。 |
| `待选择` | 没有可安全采用的值，必须由用户选择或补充 | 中性高亮标签，字段显示空值占位和下一步提示。 |
| `待修改` | 值非法或存在无法在当前字段解决的歧义 | 错误提示和具体修正动作，保存不可用。 |

颜色、图标和标签必须同时服从文字语义。不能只用红色/黄色边框表示不确定，也不能把“待确认”写成难懂的置信度数字。

## 6. 账目工作页：确认状态

### 6.1 正常识别的布局

正常识别不使用复杂表单。页面从上到下为：

1. 返回入口：`返回修改原句`。
2. 一行只读的 `原始输入：35块买菜`。
3. 五个业务字段的紧凑编辑行：金额、收入/支出、分类、备注、日期。
4. 必要的轻量提示。
5. 主按钮：`确认记账`。

字段可以直接点击编辑，不需要先进入单独的“详情”页。金额显示得最醒目，但保存仍要经过所有必填字段校验。

### 6.2 五个可编辑字段

| 字段 | 正常状态 | 修改方式 | 缺失/不确定时 |
| --- | --- | --- | --- |
| 金额 | `¥35.00` | 点击金额进入数字编辑；最多两位小数；离开后格式化展示 | 显示“待选择”或“待修改”，提示填写大于 0 的金额。 |
| 收入/支出 | `支出` | 二选一分段控件，两个选项始终可见 | 只有金额时显示“待选择”，不默认支出。 |
| 分类 | `买菜/食品` | 点击分类行展开同页的单层选项；按收支方向只显示匹配分类 | 缺失时显示“待选择”；兜底或冲突时显示“待确认”。 |
| 备注 | `买菜` | 单行文本输入，可改写或清空 | 空值显示“未填写”，不阻止保存。 |
| 日期 | `今天 · 2026年8月30日` | 使用简单日期选择器或日期输入，支持有效今天和历史日期 | 非法、未来或无法解析时显示“待修改”，保存不可用。 |

金额核心仍对应 `amount_cents` 的整数分；界面不能把支出金额展示成负数来代替“支出”标签。分类选择器只显示中文名称，保存时使用固定 code 的映射结果。

### 6.3 保存按钮

- 新增状态的主按钮文案为 `确认记账`；编辑状态为 `保存修改`。
- `ready` 且五个字段合法时，按钮可用；用户点击一次即可提交。
- 缺金额、方向、分类或日期，金额为 0/负数，出现多金额、方向冲突、非法日期、未来日期或未处理的待确认提示时，按钮禁用。
- 禁用按钮下方必须给出下一步，例如“请选择收入或支出”“请先处理分类提示”“请把日期改为今天或过去的日期”。不使用“校验失败”或内部异常名词。
- `note` 为空不影响保存。
- 保存成功后给出短反馈“已记账 ¥35.00 买菜”，来源为首页时留在首页并刷新统计/最近账目，来源为列表或编辑页时返回来源页并刷新列表。

### 6.4 original_text 的展示

- 确认页在字段之前只展示一次“原始输入”，作为核对依据，不把它复制到每个字段。
- 原句较长时默认显示两行并提供“展开原始输入”；展示按原文换行，不改写内容。
- 原句改写必须通过“返回修改原句”完成；重新解析后，新输入成为当前草稿的 `original_text`。
- 保存后编辑页显示“最初输入”，只读；普通编辑不能修改它。
- 账单列表不显示 `original_text`，避免每行信息过多。

## 7. 不确定字段与异常输入

### 7.1 没有金额：“买菜”

- 解析进入阻塞确认状态，原句仍显示“买菜”。
- 金额行显示 `待选择`，提供直接可输入的金额框，placeholder 为 `请输入金额`。
- 用户可直接补 `35`，金额字段更新后继续检查其他字段；不要求重新输入整句话。
- 也可以点击“返回修改原句”并把原句改成“35块买菜”。
- 补齐并通过校验前，`确认记账` 禁用。

### 7.2 只有金额：“35”

- 金额显示为 `¥35.00`，并标记 `待确认`，提示“未写元/块，请核对金额”。
- 收入/支出显示 `待选择`；分类也显示 `待选择`。
- 用户先选择“支出”或“收入”，再从对应固定分类中选择分类。
- 不自动猜支出，也不自动填“其他支出”。选择方向后分类列表只展示匹配的分类，避免保存收入+餐饮之类的组合。

### 7.3 多金额：“买菜35又打车20”

- 进入阻塞确认状态；金额显示 `待修改`，不要选择 35、20 或两者之和。
- 在金额行上方提示：`识别到多个金额，一次只能记一笔账。`
- 提供两个清晰动作：`返回修改原句`、`分别输入两笔`。后者只是提示用户分两次手动输入，不自动创建两条草稿。
- 返回后原句原样回填输入框，光标置于可编辑位置；用户可直接删去其中一个动作和金额，再重新识别。
- 当前草稿未处理前不能保存；输入内容不能被清空或静默改写。

### 7.4 分类兜底与分类冲突

- 已知为支出但无法稳定分类时，显示 `其他支出` 并标记 `待确认`；收入对应 `其他收入`。
- 待确认分类行同时显示一句原因和操作，例如“暂时没有更明确的分类，请确认或改选”。用户点击分类行即可在同页选择固定分类，不弹复杂对话框。
- 兜底分类必须由用户明确保留或改选后，状态才变为 `已确认`，保存按钮才可用。
- 收支方向改变后，原分类若不匹配则清空为 `待选择`，要求重新选择；不静默把收入改成支出分类。

## 8. 分类冲突的专门方案

以“带孩子吃饭86”为例：

1. 金额显示 `¥86.00`，收支显示 `支出`，日期显示今天，备注显示“带孩子吃饭”。
2. 分类默认显示 `餐饮`，右侧为 `待确认`。
3. 分类下方提示：“同时出现孩子和餐饮信息，已按核心消费行为建议餐饮。”
4. 同屏给出两个轻量操作：`保留餐饮`、`改为孩子`。点击任意一个即可完成分类确认，不打开复杂对话框。
5. 用户选择后标签变为 `已确认`，可点击一次 `确认记账`。

“吃饭”作为核心消费行为优先于“孩子”人物场景词，但用户的明确选择是最终值。列表和统计使用用户确认后的分类。

## 9. 日期体验

### 9.1 普通显示

- 未写日期默认今天，显示为 `今天 · YYYY年M月D日`。
- 昨天显示为 `昨天 · YYYY年M月D日`，前天同理；历史日期显示绝对日期，必要时保留相对词作为辅助。
- 日期控件只需支持今天、历史日期和产品规则中允许的简单日期，不提供复杂自然语言日期设置。
- 创建时间不是账务日期，界面不以“刚刚创建”替代账务日期。

### 9.2 未来日期

主 Agent 在 UX/UI 最终决策检查点正式确认：Smart Ledger V1 是记录实际发生账目的工具，不是未来预算或消费计划工具。因此 V1 不允许保存未来日期账目。

- 解析得到未来日期时保留用户原句和日期候选，不自动改成年份、昨天或今天。
- 日期行标记 `待修改`，提示：`这个日期在未来，请检查日期。`
- 日期选择器禁用未来日期；保存按钮禁用，直到用户改成有效的今天或历史日期。
- 若用户返回改写原句，原句仍保留，改写后重新解析。
- V1 不增加计划支出、未来账单、待付款或预算功能；这些都属于未来版本。

### 9.3 日期解析失败

对于无效日期或 V1 不支持的复杂日期，显示 `待修改`，提示“这个日期无法识别，请选择有效的今天或历史日期，或返回修改原句”。不把它静默当成今天。

## 10. 重复账目提醒

- 后端在保存前发现与最近一笔有效账的日期、金额、收支、分类和备注完全相同，确认页顶部显示轻量提示，不弹强制对话框。
- 推荐文案：`刚刚似乎记过一笔 ¥35.00 买菜`。
- 提供两个动作：`查看上一笔`、`仍然记账`。
- `查看上一笔` 在当前确认页展开上一笔的日期、金额、收入/支出、分类和备注摘要，不清空当前草稿；用户可折叠回到当前账。
- `仍然记账` 是用户明确继续操作，允许正常保存；重复提醒不阻止真实的重复消费。
- 不提示 `original_text` 是否相同，不把提醒做成唯一约束，不合并、覆盖或删除任何账目。

## 11. 账单列表方案

### 11.1 页面结构

1. 顶部标题 `账单`，右侧提供 `记一笔`。
2. 账目按账务日期从新到旧排列，同一天内按最近保存/修改顺序排列。
3. 可使用日期分组标题，例如 `今天`、`昨天`、`2026年8月20日`，但每行仍显示完整日期信息，避免只靠分组理解。
4. 不提供搜索、复杂筛选、图表、批量操作或分页设置；V1 只保证个人账单的直接查看。

### 11.2 每行信息

桌面端一行尽量横向排列：

`支出 | ¥35.00 | 买菜/食品 | 买菜 | 今天`

手机端允许自然换行，但信息顺序保持一致：金额和收支先读到，分类和备注随后，日期置于辅助位置。每行只显示：

- 金额
- 收入/支出
- 分类
- 备注；为空显示“未填写”
- 日期

不显示 `original_text`、商户独立字段、支付来源、创建时间、内部 code 或 `deleted_at`。

### 11.3 列表空状态和读取失败

- 空状态：“还没有账单”，下方提供“记一笔”，回到首页或直接进入账目工作页。
- 读取失败：“账单暂时加载失败，请重试。”提供“重试”，不显示 HTTP 状态码、SQLite exception 或 traceback。
- 读取失败时不要把未加载成功误显示成空列表或 `¥0.00`。

## 12. 已保存账目的查看与编辑

### 12.1 交互方案

选择 **独立账目工作页**，不使用桌面抽屉或手机弹层作为主编辑容器：

- 桌面端：从列表点击一行后进入单栏编辑页，保留顶部返回列表。
- 手机端：进入全屏编辑页，避免键盘遮挡和长表单在弹层中滚动。
- 首页最近账目和列表行都进入同一编辑状态，不另建详情页。
- 编辑页展示完整的五个业务字段，以及只读的“最初输入”。

### 12.2 编辑规则

- 金额、收入/支出、分类、备注、日期都可编辑。
- `original_text`、记录编号和系统时间不提供编辑控件。
- 修改收支后重新检查分类匹配；不匹配时分类回到 `待选择`。
- 编辑保存使用 `保存修改`，更新原账，不新建重复账。
- 取消或返回不改变原账；保存成功后列表、首页最近账目和三个统计立即按新值刷新。
- 编辑页可以显示轻量保存失败提示，并保留用户改动。

## 13. 删除和撤销

### 13.1 删除前确认

编辑页底部提供低强调的 `删除账目`。点击后出现小型确认层，只显示必要内容：

```text
确定删除这笔账吗？
今天  支出  ¥35.00  买菜/食品  买菜

[取消]                              [删除]
```

删除按钮使用危险色和明确文字；不使用“确定”这种无法说明后果的单字按钮。

### 13.2 删除成功与撤销

- 删除成功后该账从列表和首页最近账目消失，相关统计立即重新计算。
- 当前页面显示轻量提示条：`已删除这笔账   撤销`。
- 撤销入口有效时间约 10 秒；10 秒内点击 `撤销` 可以恢复原账，保留原来的金额、方向、分类、备注、日期和原始输入，并提示“已恢复”。
- 超过约 10 秒后提示条消失，当前页面不再显示撤销入口。
- 撤销失败时提示“恢复失败，原账仍未显示，请重试”，不伪装成功。
- V1 不建立垃圾桶页面、删除记录管理中心、30 天自动清理、复杂恢复系统、批量删除、永久清理或跨设备恢复。

## 14. 备份入口

- 入口位置固定在所有主页面右上角：`更多 -> 备份数据`。
- 菜单说明可以是：“下载一份本地账目备份文件。”
- 点击后显示轻量状态：`正在准备备份`，成功显示“备份文件已开始下载”，失败显示“备份暂时失败，请稍后重试”。
- 只设计入口和用户提示，不在 V1 UI 中加入恢复、导入、云端备份、定时备份或文件管理页面。
- 不要求用户理解 SQLite；文件名和技术格式由系统处理，界面不展示堆栈或数据库异常。

## 15. 错误和异常状态文案

所有错误都使用普通用户能理解的中文，并保留用户当前输入或编辑结果。

| 场景 | 用户看到的提示 | 用户操作 |
| --- | --- | --- |
| 后端/本地服务不可用 | `暂时无法连接本地服务，请确认 Smart Ledger 已启动。你刚才输入的内容仍保留。` | `重试`、继续查看当前输入；不显示 HTTP 500。 |
| 保存失败 | `这笔账还没有保存成功，内容已保留，请重试。` | `重试保存`、`继续编辑`。 |
| 账单读取失败 | `账单暂时加载失败，请重试。` | `重试`；不显示为空列表。 |
| 首页统计读取失败 | `统计暂时不可用，请重试。` | `重试`；统计显示“暂不可用”，不显示零。 |
| 解析失败/无意义输入 | `暂时没看懂这句话，请输入“金额 + 事项”，原输入已保留。` | 回到输入框继续改写；不生成“其他支出”伪账。 |
| 空输入 | `请输入一笔账，例如：35块买菜。` | 继续输入或取消。 |
| 金额为 0 或负数 | `金额必须大于 0，请修改金额。` | 直接修改金额；不取绝对值、不翻转收支。 |
| 小数超过两位 | `金额最多保留两位小数，请修改。` | 修改金额后再保存。 |
| 日期非法或不支持 | `这个日期无法识别，请选择有效的今天或历史日期，或返回修改原句。` | 选择日期或改写原句。 |
| 未来日期 | `这个日期在未来，请检查日期。` | 修改为今天或过去日期；保存保持禁用。 |
| 删除失败 | `删除没有完成，原账仍保留，请重试。` | 重试或返回。 |
| 撤销失败 | `恢复没有完成，请重试。` | 重试；不显示已恢复。 |

不向用户展示 `HTTP500`、`SQLite exception`、Python traceback、内部字段名、请求 ID 或调试日志。

## 16. 响应式行为

- V1 是普通本地 Web App，不实现 PWA、Service Worker、浏览器安装流程或手机桌面安装验收。
- 桌面端使用居中单栏工作区；首页统计可以横向排列，快速输入和账目字段保持清晰宽度。
- 手机端统计压缩为三列或可自然换行的紧凑区域，快速输入优先占据首屏；确认页字段逐行排列。
- 手机端输入框获得系统中文键盘，完成/前往动作触发解析；分类选项在同页展开，不用复杂弹窗。
- 手机端保存按钮固定在底部时，正文底部必须留出安全空间，不能遮挡备注、日期或错误提示。
- 列表行在窄屏自然换行，不截断金额、分类或日期；备注过长可折行或省略并在编辑页完整查看。
- 所有状态提示、按钮文字和错误说明在桌面与手机保持一致，不通过不同设备隐藏关键规则。

## 18. 用户完整流程

### 18.1 正常记账

`首页 -> 输入“35块买菜” -> Enter/识别 -> 账目工作页显示五个字段 -> 点击确认记账 -> 成功提示 -> 首页统计和最近账目更新`

### 18.2 缺金额

`首页 -> 输入“买菜” -> 解析 -> 金额显示待选择 -> 直接补“35”或返回改写为“35块买菜” -> 金额合法且其他字段完整 -> 确认记账`

原句仍保存为用户最终用于解析的完整原文；在确认页直接补金额不会伪造或覆盖原始输入。

### 18.3 分类不确定

`首页 -> 输入“带孩子吃饭86” -> 解析为餐饮并标记待确认 -> 点击保留餐饮或改为孩子 -> 标签变为已确认 -> 确认记账`

用户也可以在分类选择器中选择其他匹配的固定分类，最终只保存用户确认后的分类。

### 18.4 多金额

`首页 -> 输入“买菜35又打车20” -> 识别到多个金额 -> 保存禁用 -> 原句保留 -> 返回修改原句为一笔，或退出后分别输入两笔 -> 重新识别 -> 每笔单独确认保存`

系统不选第一笔、不选最后一笔、不求和、不自动创建两笔账。

### 18.5 删除撤销

`账单列表/首页最近账目 -> 点击账目 -> 编辑页 -> 删除账目 -> 二次确认 -> 软删除成功并从列表/统计移除 -> 当前页显示“已删除这笔账 撤销”约 10 秒 -> 10 秒内点击撤销恢复原账并刷新列表/统计`

撤销入口超时后提示消失，不出现垃圾桶或回收站；用户仍可看到普通错误提示，但 V1 不提供其他恢复页面。

- AI 聊天、云端大模型配置和聊天式记账
- CSV/Excel 导入、导入任务或外部平台连接
- 预算中心、年度报告、高级图表、分类占比、余额和消费建议
- 社区、好友、广告、营销首页和推荐内容
- 自定义分类、独立商户字段、独立支付来源字段
- 回收站、批量删除、复杂恢复中心和跨设备恢复
- 多主题系统、复杂动画、PWA、浏览器安装流程和离线缓存系统
- 一句话自动拆分多笔账
- 复杂设置中心

## 20. 给后续 Agent 的可验证约束

### Frontend Agent

- 按 3 个主页面和账目工作页的新增/确认/编辑状态实现，不新增设置页或详情页。
- 确认页始终显示原始输入、金额、收入/支出、分类、备注和日期；五个业务字段都可编辑。
- 识别状态要映射为“已识别、待确认、待选择、待修改”等中文表达；不把内部 code 直接展示给用户。
- 正常输入支持 Enter/手机键盘动作解析；解析失败、保存失败和返回修改都保留原句或当前编辑值。
- 保存按钮只在字段完整、歧义处理完成、日期非未来且用户明确确认时可用。
- 列表、统计和最近账目过滤已删除记录；编辑更新原账；删除后提供约 10 秒撤销。

### Backend Agent

- UI 依赖的保存闸门必须在服务端再次校验：正整数分、`type`、分类匹配、有效日期、未来日期、备注和原文长度。
- 未确认草稿不能写入数据库；重复提醒只作为可继续保存的提示。
- 删除使用软删除；统计和列表不返回已删除记录，约 10 秒内撤销恢复同一条记录。
- 备份入口对应完整 SQLite 安全备份，不由 UI 另造 JSON/CSV 导出语义。

### Test Agent

- 验证正常记账、空输入、缺金额、只有金额、多金额、分类冲突、兜底分类、0/负数、日期非法、未来日期和重复提醒。
- 验证确认页五个字段可编辑，原始输入在确认/编辑页展示但普通编辑不可修改。
- 验证保存前不更新统计，保存/编辑/软删除/10 秒内撤销后首页和列表同步更新。
- 验证空状态与读取失败状态不同，错误提示不泄露 HTTP、SQLite 或 Python 内部信息。
- 验证手机窄屏下输入、字段、错误提示和底部保存按钮不重叠，桌面端同样可完成完整流程。

### Review Agent

- 优先检查直接保存、默认支出、负数翻转、未来日期静默改写、多金额自动拆分、分类与收支不匹配、列表显示已删除账等错误。
- 检查是否出现登录、同步、导入、OCR、AI 聊天、预算、图表、设置中心或其他 V1 禁止入口。
- 检查用户看到的是中文标签，金额展示没有把支出误导为负数，原始输入没有被备注或清理副本覆盖。

## 21. 主 Agent 最终拍板结果

以下两个 UX/UI 待决问题已经在主 Agent 最终决策检查点正式确认：

1. **未来日期**：V1 可以识别未来日期，但确认区域必须提示 `这个日期在未来，请检查日期。`。未来日期没有改成今天或过去日期之前，不允许保存。V1 不增加计划支出、未来账单、待付款或预算功能。
2. **删除后撤销**：删除使用 `deleted_at` 软删除；页面立即隐藏该账目；页面显示 `已删除这笔账   撤销`；撤销有效时间约 10 秒，10 秒内点击可恢复，超过时间提示消失。V1 不增加垃圾桶页面、删除记录管理中心、30 天自动清理或复杂恢复系统。

当前没有阻塞正式开发的 UI 问题。后续 Frontend Agent 和 Backend Agent 应按本文执行；若要改变未来日期或删除恢复策略，必须先回到主 Agent 重新改动上游文档。
