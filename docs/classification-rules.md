# Smart Ledger V1 一句话记账解析与分类规则

## 文档定位与范围

- 本文是 Classification Agent 的 V1 规则契约，负责把用户的一句话转换成一笔“待确认 Transaction 草稿”。
- 本文只设计解析顺序、字段建议、分类规则、异常处理和确认边界，不创建数据库、不写前端或后端业务代码。
- 本文必须与 PROJECT.md、docs/product-v1.md、docs/data-model.md 保持一致；发现冲突时回报主 Agent，不由本 Agent 自行扩展范围。
- V1 只使用规则、关键词和正则表达式，不调用云端大模型，不要求 API Key，不把网络作为解析前提。
- 一次输入只对应一笔草稿。V1 不把一句话自动拆成多笔账。
- 任何解析结果都是建议，必须进入确认流程；用户确认前不得写入 SQLite，也不得计入首页统计。

## 1. 输出契约

### 1.1 六个固定业务字段

解析器最终只生成以下六个 Transaction 业务字段。字段名必须逐字使用，不使用 amount、raw_text、input_text、category_name 等同义字段。

| 字段 | 解析阶段的值 | 规则 |
| --- | --- | --- |
| amount_cents | 正整数分，或缺失时暂为 NULL | 金额以元输入、以分保存；大于 0；最多两位小数；不使用浮点数和负数表达方向。 |
| type | expense、income，或无法判断时暂为 NULL | 最终只能是 expense 或 income，不加入退款、转账等第三种类型。 |
| category | 固定分类的稳定内部 code，或未决时暂为 NULL/兜底 code | 只能使用 dining、groceries_food、daily_necessities、transportation、vehicle_fuel、housing、communication、entertainment、children、medical、clothing_beauty、education_learning、travel_vacation、gifts_social、pets、insurance、digital_appliances、fitness_sports、debt_repayment、taxes_fees、charity_donation、other_expense、salary、bonus、freelance、business_income、investment_income、rental_income、benefits_subsidies、pension、gift_red_envelope、other_income。 |
| note | 有意义的普通文本，或 NULL | 去掉金额、日期词和无意义的句式骨架后生成；可为空；不新增商户字段。 |
| original_text | 用户最开始输入的完整原文 | 原样保留，不把清理后的解析副本写回此字段。 |
| transaction_date | YYYY-MM-DD，或日期非法/缺失时暂为 NULL | 未写日期按规则默认当前本机日期；未来日期不能直接保存。 |

NULL 只表示草稿仍待补充或待确认，不是可直接写入数据库的最终值。正式保存前，后端仍需执行 docs/data-model.md 中的非空、长度、日期有效性和分类与 type 匹配校验。

### 1.2 解析状态和提示

为了让确认页知道该怎么提示，可以附带“解析状态”和“待确认提示”。这两项是解析流程元信息，不是 transactions 表字段，不得写入数据库，也不能替代六个固定业务字段。

| 状态 | 含义 | 是否可以进入确认流程 | 是否可以直接保存 |
| --- | --- | --- | --- |
| ready | 六个业务字段均有合法建议，未发现明显冲突 | 可以 | 不可以，仍须用户确认 |
| needs_confirmation | 有兜底分类、裸数字、分类冲突或未来日期等轻微不确定 | 可以，高亮相关字段 | 不可以，用户处理提示后才能保存 |
| needs_input | 缺金额、缺收支方向、日期非法、多金额或金额非法 | 可以进入阻塞的确认/补充状态；空输入除外 | 不可以，必须补充或修改 |
| no_draft | 空输入或完全无记账意义的内容 | 不进入正常确认页 | 不可以 |

解析器可以在提示中写明“缺少金额”“请选择收入或支出”“请拆成两笔分别输入”等，但不能把提示当作新的 Transaction 字段。

## 2. 推荐解析顺序

解析必须按以下顺序执行。顺序的目的不是追求复杂智能，而是让每一步使用清晰的输入、减少把日期数字当金额、把人物场景误当分类或把不确定性静默吞掉的风险。

| 步骤 | 处理内容 | 具体规则 | 原因 |
| --- | --- | --- | --- |
| 1 | 保留 original_text | 先保存用户最开始输入的完整字符串；不删除字词、不重排、不用后续清理结果覆盖。 | 让用户能核对原句，也为后续排查规则误判保留依据。 |
| 2 | 清理解析副本 | 复制一份临时文本，只在副本上去除首尾空白、合并无意义空白、识别通用标点；保留原文不变。先标记日期片段，避免日期中的数字参加金额匹配。 | 把“便于匹配”与“原文追溯”分开，避免破坏 original_text。 |
| 3 | 识别日期 | 按本文件支持的简单日期规则识别，并把最终日期统一成 YYYY-MM-DD；未写日期默认今天。 | 日期数字形如 8月20日 或 2026-08-20，不能误报为金额。 |
| 4 | 识别金额 | 在排除已确认日期数字后，寻找金额候选；将元字符串按规则转换为 amount_cents。 | 金额是保存的关键字段，必须先处理 0、负数、小数位和多金额。 |
| 5 | 判断收入/支出 | 根据明确收入词、消费行为词和上下文判断 type；没有可靠依据时留空，不设置掩盖不确定性的全局默认支出。 | 方向错误会直接影响统计，不能为了“识别成功”而乱猜。 |
| 6 | 判断分类 | 依据核心消费行为、物品/服务词和场景词命中分类 code；处理人物词与消费行为词的冲突。 | 分类需要稳定 code，且必须与 type 匹配。 |
| 7 | 生成 note | 从解析副本中去掉金额、日期词和明显句式骨架，保留有意义的描述文本。 | 备注是辅助追溯，不应重复堆放已存入其他字段的解析元素。 |
| 8 | 检查缺失和冲突 | 检查金额、方向、分类、日期是否缺失或非法；检查多金额、收入与支出同时出现、分类冲突、未来日期等。 | 将不确定性显式交给确认页，而不是静默生成错误账目。 |
| 9 | 生成待确认结果 | 组装六个固定字段，并附带解析状态、缺失项、候选项和提示；完整建议也只属于待确认草稿。 | 保证后续 UX/UI、Frontend 和 Backend 使用同一份可解释结果。 |
| 10 | 用户确认后才允许后续保存 | 用户检查并可修改金额、收支、分类、备注、日期；所有必填字段合法且歧义处理后，才交给保存流程。 | 这是 V1 的核心安全边界，解析器没有直接保存权限。 |

## 3. 解析副本和原文边界

解析副本可以做以下有限处理：

- 去除首尾空白，便于判断空输入；
- 将连续空白视为一个分隔；
- 识别日期、金额和常见标点边界；
- 在生成 note 时移除已经确定属于金额或日期的片段。

解析副本不做以下处理：

- 不把“买菜”改写成“食品”；
- 不把中文分类名称写入 category，category 始终保存 code；
- 不用关键词命中顺序代替冲突判断；
- 不把未识别的内容擅自删除；
- 不把副本重新拼接成 original_text。

## 4. 金额识别规则

### 4.1 支持的金额形式

V1 支持阿拉伯数字金额。数字可以出现在消费/收入词之前或之后，单位可以有也可以没有。

| 输入形式 | 识别结果 | 说明 |
| --- | --- | --- |
| 5块买菜 | amount_cents = 500 | 5 是整数元；块是金额单位。 |
| 5元买菜 | amount_cents = 500 | 元是金额单位。 |
| 35.8元吃饭 | amount_cents = 3580 | 一位小数按角处理，末尾补一个 0 分。 |
| 35.80买菜 | amount_cents = 3580 | 没有单位也可以识别；因是裸数字，确认页提示核对单位。 |
| 加油300 | amount_cents = 30000 | 金额在关键词之后。 |
| 工资8000 | amount_cents = 800000 | 金额在关键词之后，方向由“工资”判断为收入。 |
| 20打车 | amount_cents = 2000 | 金额在关键词之前；无单位时仍可作为单一金额候选。 |

### 4.2 数字和转换规则

1. 整数元直接乘以 100：5 元变为 500 分，300 元变为 30000 分。
2. 一位小数按元和角转换：35.8 元变为 3580 分；不使用浮点数进行核心计算。
3. 两位小数直接按分转换：35.80 元变为 3580 分。
4. 小数点后超过两位时不四舍五入、不截断，标记金额非法，要求用户改成最多两位小数。
5. 元、块是 V1 明确支持的常见单位；可以把紧邻的“块钱”作为“块”的同义写法处理。其他货币单位、中文大写数字、复杂口语金额、带逗号的复杂格式不在 V1 自动解析范围内，需用户改写或在确认页手动填写。
6. 只有一个候选裸数字时可以生成金额建议，但确认页应提示“未写元/块，请核对金额”；不能因为没有单位就把它当作别的字段。
7. 日期片段中的数字必须先从金额候选中排除。例如 2026-08-20 是日期，不是金额；8月20日买菜只有后续明确金额时才能生成完整草稿。
8. 金额正负只表示输入是否合法，不承担收支语义。-5元不自动改成 5 元支出，也不自动改成收入。
9. 0 或 0.00 是非法金额；不能用 0 表示“稍后填写”。
10. 金额转换后的 amount_cents 必须是正整数，且必须能被后端/SQLite 的整数范围安全表示。可表示但明显偏大的金额进入确认页并高亮核对；超过安全整数范围时阻塞，不静默溢出。

### 4.3 多金额和缺金额

- 识别日期后仍有两个或更多金额候选时，视为“多金额歧义”。amount_cents 不选择第一个、最后一个或总和，保持待定。
- V1 不自动拆分多笔，也不自动创建两条草稿。确认页应提示用户把原句改写成一笔，或者拆成两次分别输入；“拆成两笔”是用户的操作，不是解析器的自动行为。
- 只有一个金额时，金额可以先进入确认页；没有金额时保留原句和其他可识别字段，金额留空并阻止保存。
- 只有金额的输入，例如 35，金额可以确定，但 type 和 category 不可从数字本身推断，不能默认支出。

## 5. 收入/支出判断规则

### 5.1 两个固定值

type 只能是：

- expense：支出，钱从用户可支配资金中流出；
- income：收入，钱进入用户可支配资金。

支出金额和收入金额在 amount_cents 中都保存为正整数，方向完全由 type 表示。

### 5.2 关键词分组

| 方向 | 强提示词和典型词 | 处理原则 |
| --- | --- | --- |
| 支出 expense | 买、购买、花了、支付、付款、消费、支出、吃饭、吃面、早餐、午饭、晚饭、奶茶、咖啡、买菜、食品、水果、买东西、打车、公交、地铁、加油、停车、话费、看病、挂号、买药、电影、游戏、衣服、教育、旅行、送礼、宠物、保险、手机、健身、还款、税费、捐款 | 这些词表示已经发生消费或资金流出；结合分类表生成支出建议。 |
| 收入 income | 工资、薪资、月薪、发工资、工资到账、奖金、绩效奖金、年终奖、提成、兼职、劳务费、接单收入、经营收入、副业收入、分红、股息、投资收益、利息收入、理财收益、租金收入、收租、补贴、津贴、福利、补助、养老金、退休金、红包收入、收到红包、礼金到账、收入、收款、收到、到账、赚到 | 这些词表示资金流入；“工资”优先到 salary，明确奖金、兼职、经营、投资、租赁、补贴、养老金和红包/礼金分别建议对应固定收入分类，泛化收入词回退到 other_income 并提示确认。 |

词表只用于可解释的规则命中，不把单个模糊词当作绝对真相。例如“收到”需要结合上下文；若同时出现收入和支出含义，则进入冲突处理。

### 5.3 默认支出和不确定性

- V1 不设置“任何没有收入词的内容都默认支出”的全局规则。
- 当文本出现明确消费行为或支出项目时，例如“买菜”“吃面”“加油”“打车”，可以生成 expense 建议；即使方向词没有单独出现，消费行为本身已经是支出证据。
- 只有金额、只有“记账”、只有“钱”等中性输入，不足以判断方向；type 留空，要求用户在确认页选择。
- 输入含明确收入词时生成 income；如果同时出现明确支出行为，不按词出现顺序选择一边。
- 任何规则命中都只是建议，最终方向必须由用户确认；不确定方向属于关键缺失，未选择前不能保存。

### 5.4 收入与支出同时出现

一条输入同时表示两次资金动作时，例如“工资到账后交房租8000”，一笔 Transaction 无法同时表达两件事。处理规则如下：

1. 标记“同时包含收入和支出含义”，type 留空或标记为冲突，不用收入词或支出词的先后顺序消解。
2. 若可以识别两个消费/收入对象，也同时标记多动作；不要因为只有一个数字就假装它是一笔明确账。
3. 允许进入阻塞确认状态，保存按钮不可用；提示用户改写为一笔，或分别输入两笔。
4. 用户如果明确在确认页选择一个方向，仍只能保存一笔，并且必须确认金额、分类和备注确实只对应这一笔；解析器不替用户决定哪一笔被舍弃。

| income | benefits_subsidies | 补贴/福利 | 补贴、津贴、福利、补助 | 津贴500 |
| income | pension | 养老金 | 养老金、退休金、退休工资 | 退休工资3000 |
| income | gift_red_envelope | 红包/礼金 | 红包收入、收到红包、礼金到账、收到礼金 | 收到礼金200 |
| income | other_income | 其他收入 | 收入、收款、收到、到账、赚到以及其他无法稳定命中具体收入分类的流入项目 | 收到一笔钱500 |

分类词命中后仍要进行收支匹配：例如“工资”不能保存为 dining，“买菜”不能保存为 salary。用户在确认页把 type 改成另一方向时，必须重新选择与新方向匹配的分类。

## 7. 分类冲突规则

### 7.1 先判断词的角色

不能简单采用“哪个关键词先出现就选哪个分类”。每次分类至少区分以下三类线索：

1. 核心消费行为或消费对象：实际买了什么、吃了什么、乘坐什么、支付了什么服务，例如“吃饭”“买菜”“打车”“加油”“挂号”。
2. 人物/场景词：谁参与、谁受益或发生在哪个场景，例如“孩子”“带孩子”“给朋友”“出差”。它们通常是修饰信息，不自动覆盖核心消费行为。
3. 方向或句式骨架：例如“花了”“到账”“记一笔”。这些词帮助判断 type，通常不单独决定分类。

### 7.2 冲突决策

- 有明确核心消费行为时，核心行为优先于人物/场景词。例如“带孩子吃饭86”中，“吃饭”是消费行为，默认分类为 dining；“孩子”作为冲突提示和备注内容保留。
- 只有人物/场景词，并且消费对象很泛时，人物/受益人可以成为主要分类。例如“给孩子买东西80”没有具体物品或服务，分类为 children。
- 如果是孩子专属的明确项目，例如“买奶粉”“买尿布”“孩子学费”，直接倾向 children；如果同时明确“带孩子吃饭”，仍以实际消费行为 dining 为主，除非用户在确认页改选 children。
- 如果两个核心消费行为同样明确但没有多金额，例如“吃饭和打车50”，不能凭词序挑选；给出候选分类 dining、transportation，分类待确认，并提示原句可能包含两个动作。
- 如果没有足够线索，支出使用 other_expense 作为明确兜底建议并高亮；收入使用 other_income 作为明确兜底建议并高亮。候选分类以内部 code 提供给确认层，最终必须由用户选择或确认。
- 不为了填满 category 而编造新 code，不把中文名称直接作为保存值。

### 7.3 代表性冲突示例

| 输入 | 核心判断 | 默认 category | 确认提示 |
| --- | --- | --- | --- |
| 带孩子吃饭86 | “吃饭”是实际消费行为；“孩子”是人物场景词 | dining | 高亮分类，提示“同时出现孩子和餐饮信息，已按核心消费行为建议餐饮，可修改”。 |
| 给孩子买东西80 | 没有具体消费品/服务；“给孩子”说明受益人 | children | 可以正常确认；用户若实际买的是食品、日用品等，可改选对应分类。 |
| 孩子买奶粉200 | “奶粉”是孩子专属消费对象 | children | 可以正常确认。 |
| 吃饭和打车50 | 两个核心行为并列，无法确认唯一分类 | other_expense，候选 dining、transportation | 高亮分类，建议改写或选择一个分类；不自动拆分。 |

## 8. 日期识别规则

### 8.1 V1 支持范围

设解析时读取的当前本机日期为 D，当前年份为 Y。所有日期先验证真实日历，再统一输出 YYYY-MM-DD。

| 输入日期表达 | 输出规则 | 示例说明 |
| --- | --- | --- |
| 未写日期 | 使用当前本机日期 D | 5块买菜在当天得到 D。 |
| 今天 | 使用 D | 不保存“今天”这个词。 |
| 昨天 | 使用 D - 1 天 | 跨月、跨年时按真实日历计算。 |
| 前天 | 使用 D - 2 天 | 仅支持“前天”，不扩展更多相对日期。 |
| 8月20日、8月20号 | 使用 Y-08-20 | 按当前年份解释；必须是有效日期。 |
| 2026-08-20 | 使用明确的 2026-08-20 | 年、月、日必须完整且有效。 |
| 2026年8月20日、2026年8月20号 | 使用明确的 2026-08-20 | 中文年月日格式只支持这一类简单表达。 |

### 8.2 当前年份未到的月日

8月20日 或 8月20号永远先按当前年份 Y 解释。如果当前本机日期还没有到 Y-08-20：

- transaction_date 仍输出 Y-08-20，不自动改成上一年；
- 解析状态为 needs_confirmation，提示用户这是未来日期；
- V1 不直接保存未来日期，用户必须在确认页改成有效的今天或历史日期，或者返回改写原句；
- 不能静默猜测用户其实想写上一年。

明确年份的未来日期也遵循同样原则：保留用户给出的日期、标记并阻止保存，不能静默改写。

### 8.3 非法和不支持的日期

- 2月30日、2026-13-01、2026年2月30号等日期解析失败，transaction_date 留空，进入阻塞确认状态。
- 如果文本明确出现了不支持的日期意图，例如“上周三”“去年春节前一天”“下个月最后一天”，不能把它当作“未写日期”而默认今天；要求用户改成支持的表达或在确认页直接选择有效日期。
- V1 不设计农历、日期范围、时分秒、复杂节假日、模糊星期和多级自然语言日期系统。

## 9. note 生成规则

note 是唯一的自由文字备注字段。生成目标是保留用户真正想记的描述，不追求复杂自然语言理解。

### 9.1 处理顺序

1. 从解析副本中移除已识别金额及其紧邻的“元”“块”“块钱”。
2. 移除已识别日期表达：今天、昨天、前天、支持的月日和年月日；可移除只用于时间定位的“早上”“中午”“下午”“晚上”。
3. 移除明显的句式骨架，例如单独承担方向作用的“花了”“记账”“记一笔”“到账”；如果一个词本身是有意义的项目或分类名称则保留，例如“工资”“话费”“买菜”。
4. 清理多余标点和空白，但不改写剩余文字的意思。
5. 剩余内容有意义则作为 note；没有有意义内容则为 NULL。

### 9.2 备注边界

- note 可以保留商户名、地点或人物描述，但 V1 不把它们提升为独立字段。
- 不把金额、日期词原样重复放入备注；“晚上”这类时间修饰词在不影响语义时可去掉。
- 不能为了生成备注而使用复杂 NLP、联想补词或替用户编造商品名称。
- note 超过 200 个字符时提示用户修改，不静默截断；确认页仍允许用户清空或改写。
- 备注为空时保存为 NULL，不写入“无备注”等伪造文本。

## 10. original_text 原样保留规则

- original_text 必须保存用户最开始输入的一句话，例如用户输入“昨天晚上带孩子吃饭86”，草稿的 original_text 就是“昨天晚上带孩子吃饭86”，不能变成“带孩子吃饭”。
- 解析日期、金额、分类和备注时只能使用临时解析副本；不能删除金额、日期词或关键词后覆盖 original_text。
- 原文中的文字顺序、内部空格、标点和用户措辞都应保留。原文不是 note 的同义字段。
- 用户在确认前返回并改写原句时，重新解析后使用用户新提交的完整原句作为新的 original_text；旧句不作为另一笔账保存。
- 用户确认并保存后，普通编辑只允许修改 amount_cents 对应金额、type、category、note 和 transaction_date，不修改 original_text。
- 空字符串不能形成正式账目；长度超过 500 个字符时要求用户缩短，不静默截断。
- 本规则要求解析草稿逐字符保留原文；正式保存仍需遵守 docs/data-model.md 的长度和空值校验。无论保存层如何做首尾空白校验，都不能把解析副本或 note 写成 original_text，也不能删除原文中间的内容。

## 11. 异常输入和失败处理

下表中的“允许进入确认页”指是否可以展示一个保存按钮被禁用的待处理状态；它不代表可以绕过确认保存。空输入和完全无意义输入不进入正常确认页。

| 异常输入 | 是否允许进入确认页 | 草稿中的缺失/异常字段 | 用户需要补充或修改什么 |
| --- | --- | --- | --- |
| 空输入 | 否；停留在输入状态 | 不生成草稿；original_text 为空 | 输入一句有金额的记账描述，或取消。 |
| 没有金额，例如买菜 | 是，进入阻塞确认状态 | amount_cents 缺失；其余能识别的字段可保留 | 补一个大于 0 的金额，或返回修改原句。 |
| 只有金额，例如 35 | 是，进入阻塞确认状态 | type、category 缺失；amount_cents 可为 3500；日期默认今天 | 选择 expense/income，再选择匹配的分类。不能默认支出。 |
| 多个金额，例如买菜35又打车20 | 是，进入阻塞确认状态 | amount_cents 不确定；分类可以给多个 code 候选；不自动拆分 | 改写成一笔，或拆成两次输入分别确认；不能让解析器自动创建两笔。 |
| 无法判断分类 | 是，方向已知时给兜底并高亮 | 支出建议 other_expense，收入建议 other_income；最终分类待确认 | 从固定分类中选择，或明确确认对应的其他分类；不能自定义新 code。 |
| 无法判断收入/支出 | 是，进入阻塞确认状态 | type 缺失；分类暂不确定或仅保留候选 | 选择 expense 或 income，然后选择匹配分类。 |
| 日期解析失败 | 是，进入阻塞确认状态 | transaction_date 缺失或非法 | 使用今天、昨天、前天、有效的月日或明确年月日，或在确认页选有效日期。 |
| 金额为 0 | 是，进入阻塞确认状态 | amount_cents 非法，不把 0 当占位值 | 输入大于 0 的金额。 |
| 负数金额，例如 -5元 | 是，进入阻塞确认状态 | amount_cents 非法；不自动取绝对值、不翻转 type | 改成正数，并明确选择收入或支出。 |
| 极大金额 | 是，但金额必须高亮核对 | 可表示的极大整数保留建议；超出安全整数范围则 amount_cents 非法/缺失 | 核对元和分的位数，重新输入可安全表示且确实正确的金额；不因金额大就自动改小。 |
| 无意义输入，例如你好、随便记一下 | 不进入正常确认页；可展示补充提示 | 没有金额，也没有可解释的方向/分类线索 | 重新输入“金额 + 事项/收入含义”；不生成伪造的其他分类账。 |
| 同时包含收入和支出含义 | 是，进入阻塞确认状态 | type 冲突；可能同时有多个动作和分类候选 | 改写成一笔，或分别输入两笔；不得按关键词顺序自动选择。 |

补充校验：金额小数超过两位、原文超过 500 个字符、备注超过 200 个字符、分类与 type 不匹配时，也必须阻止保存并给出具体修改提示。

## 12. 用户确认规则

### 12.1 三种确认状态

- **完整建议**：金额、方向、分类、备注和日期都有合法建议，进入正常确认页。用户仍必须检查并点击确认/保存，解析器不得直接落库。
- **轻微不确定**：例如裸数字、other_expense/other_income 兜底、人物词和消费行为词冲突、当前年份月日尚未到。进入确认页并高亮不确定字段；用户明确确认或改选后才能继续。
- **关键数据缺失或非法**：例如无金额、多金额、方向未知、日期非法、0 或负数。可以展示阻塞确认/补充状态，但保存按钮不可用，直到用户补充或修改。

### 12.2 确认页至少可修改

用户必须能够修改以下字段：

- 金额，对应最终的 amount_cents；
- 收入/支出，对应 type；
- 分类，从固定 code 映射的分类列表中选择 category；
- 备注，对应 note，可以填写、修改或清空；
- 日期，对应 transaction_date，必须是有效且不晚于当前本机日期的日期。

遇到多金额、表达不清或原句明显写错时，用户还应能返回输入状态改写原句并重新解析。改写后，新的原句才成为当前草稿的 original_text。

### 12.3 保存闸门

只有同时满足以下条件，后续保存流程才可以被调用：

1. 用户已看到完整原句和六个业务字段；
2. amount_cents 是大于 0 的整数；
3. type 是 expense 或 income；
4. category 是允许的 code，且与 type 匹配；
5. transaction_date 是有效的 YYYY-MM-DD，且不是未来日期；
6. 多金额、方向冲突、日期未来、兜底分类等提示已经由用户处理；
7. 用户明确确认保存。

note 可以是 NULL，不因没有备注而阻止保存。确认后的字段才是最终 Transaction 值；确认前的草稿不进入列表和统计。

## 13. 重复提醒边界

Classification Agent 不禁止重复，也不因为输入看起来重复而拒绝草稿。数据库允许真实重复交易，重复提醒由后端/API 在保存前做简单比较。

后端可以把当前待保存的五个业务值与最近一笔有效账比较：

transaction_date + amount_cents + type + category + note

比较范围只包括 deleted_at IS NULL 的已保存记录，且按数据模型的简单边界只提醒最近一笔完全相同的账。original_text 不作为重复判定条件，因为同一笔真实消费可能被用户用不同措辞重新输入。

如果后端返回“可能重复”，确认页提示用户选择返回修改或仍然保存。用户明确继续后仍允许保存；Classification 不自动合并、覆盖、删除，也不扫描所有历史记录设计复杂去重算法。

## 15. 再次判断 V1 是否需要 AI

### 15.1 V1 结论

V1 不需要 AI，也不应把 AI API 作为第一版可用前提。规则、关键词和正则已经足够支撑当前范围：

- 金额格式有限且可明确转换为整数分；
- 日期只覆盖今天、昨天、前天、简单月日和明确年月日；
- 收支方向和基础分类有稳定词表；
- 用户在确认页可以修改结果；
- 本地规则可解释、可离线运行、不会把原句发送到云端；
- 多金额、方向冲突和分类不确定时，明确转人工确认比冒险猜测更适合新手账目。

Research 决策应把“规则覆盖规定样例 + 不确定时可修改”作为 V1 的成功标准，而不是把“像人一样理解所有自然语言”作为目标。复杂长句、隐含语义、多个动作、模糊日期和无法稳定分类的表达，V1 优先进入确认页或要求用户改写。

### 15.2 未来 AI 的合理插入点

如果未来研究证明规则覆盖不足，AI 最适合作为“规则解析后的可选辅助建议器”，插在：

1. 规则完成日期和金额的确定性提取之后；
2. type、category、note 的候选生成和冲突检查之前或其中；
3. 只处理规则无法判断或产生多个候选的原句；
4. 输出仍然映射到同一套六个字段和待确认状态；
5. AI 不能绕过用户确认，不能直接保存，也不能未经单独授权把 original_text 发往云端。

金额、日期和保存闸门仍应以确定性校验为主。当前文档不引入任何 AI API、模型配置、网络依赖或 AI 置信度字段。

## 16. 给后续 Agent 的读取建议

### UX/UI Agent

- 设计输入、解析、确认、保存和失败提示的状态流，区分 ready、needs_confirmation、needs_input 和空输入。
- 确认页必须展示 original_text、金额、收入/支出、分类、备注和日期；待确认字段要高亮但不能用难懂的内部 code 直接面对普通用户。
- 处理多金额时提供“返回改写”或“分别输入两笔”的清晰路径，但不要做自动拆分。
- 覆盖缺金额、只有金额、方向不明、分类兜底、带孩子吃饭冲突、未来日期、0/负数、无意义输入和重复提醒。
- 设计字段修改入口：金额、收入/支出、分类、备注、日期均可改；原句改写应回到输入状态重新解析。

### Frontend Agent

- 按固定字段名消费解析结果：amount_cents、type、category、note、original_text、transaction_date。
- 将 category code 映射为中文标签展示；不要把中文名称写回 category，不要另造 amount 或 raw_text。
- 把解析状态、缺失项、候选项和提示当作确认流程元信息，不把它们当作数据库 Transaction 字段。
- 对 NULL 备注显示为空值状态；对待定金额、方向、分类或日期禁用保存，并保留原句。
- 金额展示由 amount_cents 转换，核心状态不使用浮点金额。

### Backend Agent

- 实现时复现本文件的确定性规则，并在 API 边界再次校验金额、方向、分类 code、备注长度、原文长度、有效日期和未来日期。
- expense 只能配支出分类，income 只能配收入分类；不得接受本表之外的 code。
- 未确认草稿不写入 SQLite；保存只接受已经确认且字段完整的结果。
- 多金额、0、负数、日期非法和方向冲突必须返回可理解的错误/提示，不静默修复。
- 按 docs/data-model.md 保持正整数分、transaction_date 与创建时间分离、original_text 追溯不被普通编辑覆盖。
- 重复提醒只做后端/API 的简单最近一笔比较，不建立唯一约束，不合并真实重复账。

### Test Agent

- 覆盖本文 20 个案例、所有 32 个固定分类 code、收入/支出与分类匹配，以及金额整数、小数一位/两位、裸数字和前后置关键词。
- 用可注入的本机日期验证今天、昨天、前天、当前年份月日、跨月跨年、非法日期和未来日期；不要把测试绑定到真实今天。
- 验证多金额不自动拆分、不选择首个/最后一个、不自动求和；验证 0、负数、超过两位小数和极大金额边界。
- 验证 original_text 与解析副本分离，note 去掉金额/日期词但保留有意义内容；验证空备注为 NULL。
- 验证确认前不保存、不统计，确认页修改五个可编辑业务字段后只保存用户确认的最终值。
- 验证重复账允许保存且只产生提醒，不把提醒做成唯一约束或强制拒绝。

### Review Agent

- 逐项检查解析顺序、字段名、32 个固定 code、type 枚举、整数分和 YYYY-MM-DD 是否与数据模型一致。
- 优先检查错误记账风险：默认支出掩盖不确定性、负数翻转方向、日期数字误作金额、分类冲突按词序误判、收入分类配支出 code。
- 检查是否存在直接保存、自动拆分、云端 AI 依赖、真实账目写入或新增 merchant、source、置信度等 V1 禁止字段。
- 检查 original_text 是否被清理后的 note 覆盖，重复提醒是否错误阻止合法重复账。

### 主 Agent

- 先验收本文是否覆盖“自然语言输入 -> 待确认 Transaction 草稿 -> 用户确认后保存”的完整边界，再决定是否进入 UX/UI 和接口契约阶段。
- 继续保持 Classification Agent 只拥有 docs/classification-rules.md 的文件边界；不要因本规则直接创建 frontend/、backend/、数据库或业务代码。
- 以本文的分类 code、20 个案例和异常处理作为后续实现与测试的输入；若要增加词、字段、日期表达或 AI，先修改并确认 V1 范围。
- `original_text` 已与 docs/data-model.md 对齐：保存用户提交的原始字符串本身；保存层只做有效内容和长度校验，不能用清理后的解析副本覆盖。

## 17. 需要 UX/UI Agent 后续决定的问题

以下只属于交互呈现，不改变本文的解析和数据边界：

1. needs_confirmation 字段采用颜色、图标还是文字提示高亮，以及提示文案的具体措辞。
2. 多金额输入是先进入一个保存禁用的确认页，还是直接进入“请拆分输入”的补充状态；两者都不能自动创建两笔账。
3. other_expense/other_income 兜底分类的默认展示、确认文案和分类选择器的具体顺序。
4. 当前年份尚未到的月日、未来日期和日期解析失败分别使用怎样的错误提示与日期控件状态。
5. original_text 在确认页和详情页的展示位置、折行方式和长度超限提示；不得把它变成列表核心列或可随普通编辑静默改写的字段。
6. 可能重复提醒的展示位置、按钮文案和“继续保存”的二次确认方式；不能把提醒变成强制去重。

本 Agent 不对这些视觉和交互细节作实现决定。除上述呈现问题外，V1 的字段、分类、解析顺序、异常安全边界和确认后保存规则已在本文固定。
