# Smart Ledger / 智能记账 APP V1 产品需求

## 文档定位

- 状态：V1 产品基线，供 Research、Data、Classification、UX、UI、Frontend、Backend、Test、Review Agent 共同读取。
- 目标：定义个人长期自用的本地智能记账工具的最小可用闭环。
- 产品对象：不要求专业财务知识的个人用户，默认单人、本地使用。
- 约束：V1 是本地 Web App，使用规则和关键词解析，不强制依赖云端大模型，数据存储使用 SQLite。
- 本文是产品范围和行为的依据。任何新增字段、页面、入口或自动化能力都必须先由主 Agent 修改并确认本文，不得由后续 Agent 自行扩展。

## 1. V1 能力与目标

### 1.1 核心能力

用户输入一句自然语言记账描述，系统提取金额、收支方向、分类、备注和日期，用户在确认页面检查或修改后保存；保存后的账单可以在账单列表中查看、编辑、删除，首页实时显示今天支出、本月支出和本月收入。

### 1.2 成功定义

V1 只需要稳定完成这一条链路：

`用户输入一句话 -> 规则识别 -> 用户确认或修改 -> 保存 -> 账单列表查看 -> 编辑或删除 -> 首页汇总`

识别结果永远是待确认结果，不得绕过确认页面直接写入账单。

### 1.3 固定产品边界

- 仅支持本地单用户使用，不建立账号体系。
- 解析以确定性的规则和关键词为主，结果需要可解释、可修改。
- 不要求联网，不把云端大模型作为 V1 的可用前提。
- 账单必须能在本地持久保存，关闭并重新打开应用后仍可查看。
- 一次自然语言输入只对应一笔账；V1 不自动把一句话拆成多笔账。
- 一笔账只有一个金额、一个收支方向、一个分类、一个备注和一个日期。

## 2. 正常记账流程

### 2.1 流程步骤

1. 用户从首页快速记账入口进入输入状态。
2. 用户输入一句话，例如“5块买菜”，点击识别或继续。
3. 系统按 V1 规则识别金额、收支方向、分类、备注和日期，并明确展示识别结果。
4. 用户进入确认页面，检查结果；发现错误时可以修改字段，必要时返回修改原句。
5. 用户点击保存。字段不完整或存在未处理的歧义时，保存按钮不可用或要求先处理提示。
6. 保存成功后显示明确反馈，新账单立即出现在账单列表顶部；首页相关汇总和最近账单同步更新。

### 2.2 流程不变量

- 没有金额、收支方向或分类等必需信息时，不得静默保存。
- 系统的猜测只能作为建议，用户确认后的字段才是最终账单内容。
- 保存、编辑、删除都应有明确的成功或失败反馈。
- 识别失败不应清空用户原句；用户可以继续修改或取消。

## 3. 输入规则与样例识别结果

### 3.1 基本规则

- 金额识别支持样例中的阿拉伯数字及常见金额单位“块”“元”；没有单位时，连续数字仍可作为金额候选，但必须在确认页核对。
- 金额必须是大于零的数值，V1 不把负数自动转换为收入或支出。
- “今天”表示当前本地日期，“昨天”表示当前本地日期的前一天；未出现日期时默认今天。
- “工资”等明确收入词优先判断为收入；买菜、吃面、午饭、加油、打车、买东西等消费语义优先判断为支出。
- 分类由关键词和语义词表决定，识别结果必须能在 V1 分类列表中选择。
- 对无法确定的字段不擅自猜测，交由确认页面处理。
- 用户确认前可以看到原始输入，原始输入不作为单独的账单展示字段。

### 3.2 规定样例

以下结果是 V1 对给定样例的默认建议。日期中的“今天”以实际保存当天为准，“昨天”以保存当天的前一天为准。所有结果仍需用户确认。

| 用户输入 | 金额 | 收支 | 分类 | 默认备注 | 日期 |
| --- | ---: | --- | --- | --- | --- |
| `5块买菜` | 5 | 支出 | 买菜/食品 | 买菜 | 今天 |
| `18块吃面` | 18 | 支出 | 餐饮 | 吃面 | 今天 |
| `300加油` | 300 | 支出 | 车辆/加油 | 加油 | 今天 |
| `20打车` | 20 | 支出 | 交通 | 打车 | 今天 |
| `8000工资` | 8000 | 收入 | 工资 | 工资 | 今天 |
| `昨天买菜35` | 35 | 支出 | 买菜/食品 | 买菜 | 昨天 |
| `今天午饭15块` | 15 | 支出 | 餐饮 | 午饭 | 今天 |
| `给孩子买东西80` | 80 | 支出 | 孩子 | 给孩子买东西 | 今天 |

默认备注只保留去除金额、日期和明显收支词后的描述性文字；用户可以清空或改写备注。若无法提取有意义的描述，备注为空，不影响保存。

## 4. 一笔账的字段与 V1 决策

### 4.1 用户可见字段

| 字段 | 是否必填 | 产品要求 |
| --- | --- | --- |
| 金额 | 是 | 只能是大于零的数值；确认页可修改。 |
| 收入/支出 | 是 | 只能选择“收入”或“支出”；不得默认为支出来掩盖不确定性。 |
| 分类 | 是 | 只能从 V1 固定分类中选择；确认页可修改。 |
| 备注 | 否 | 可为空；默认从原句提取，可编辑。 |
| 日期 | 是 | 默认今天；识别“昨天”等日期词；确认页可改为有效历史日期。V1 不处理未来账单。 |

### 4.2 商户和来源是否进入 V1

- 商户不进入 V1 的独立字段。系统不要求识别、维护或展示结构化商户名称。
- 账单来源不进入 V1 的独立字段。V1 不区分现金、银行卡、微信、支付宝或其他支付来源。
- 如果原句里出现商户或来源文字，可以作为备注的一部分保留和编辑，但不增加新的筛选、统计或同步能力。
- 以上决定避免在核心闭环中引入支付渠道、外部平台和额外字段。

## 5. 确认页面

### 5.1 用户看到的内容

确认页面必须同时展示：

- 用户刚输入的原句，便于核对。
- 识别后的金额。
- 收入/支出方向。
- 分类。
- 备注。
- 日期。
- 识别提醒或异常提示，例如“分类需要确认”“发现多个金额”。
- 明确的保存按钮，以及返回或取消当前输入的入口。

### 5.2 用户可以修改的内容

- 金额：修改为一个大于零的金额。
- 收入/支出：在收入和支出之间重新选择。
- 分类：从最终分类列表中重新选择，不允许在 V1 临时创建新分类。
- 备注：填写、修改或清空。
- 日期：选择今天或有效历史日期。
- 原句：遇到多个金额、表达不清等问题时，可以返回输入状态改写原句。

### 5.3 保存按钮规则

- 所有必填字段有效且歧义已处理后，保存按钮可用。
- 空输入、无金额、两个金额未处理、收支方向未确定、金额为负数等情况，保存按钮不可用并给出下一步提示。
- 分类使用“其他支出”或“其他收入”时，必须在页面上明确标记为待确认；用户确认分类后才能保存。
- 保存成功后给出成功反馈，并让新账单可在账单列表中立即看到。

### 5.4 分类错误的处理

用户发现分类错误时，直接打开分类选择器并改选正确分类，然后保存。系统不要求用户重新输入整句话，也不自动创建用户未确认的分类。修改后的分类是最终值，后续首页汇总和账单列表都使用修改后的值。

## 6. 账单列表

### 6.1 每行展示内容

每一行至少展示：

- 金额。
- 收入或支出标识。
- 分类。
- 备注，没有备注时显示清晰的空值状态而不是伪造文字。
- 日期。

商户、支付来源和原始输入不作为单独列展示。

### 6.2 查看

- 用户可以从首页最近账单进入完整账单列表。
- 默认按日期从新到旧排列；同一天内按最近保存顺序排列。
- 用户点击一行可以查看该笔账的完整字段，并进入编辑。
- 没有账单时显示明确的空状态和快速记账入口。
- V1 不提供搜索、复杂筛选、图表报表或批量操作。

### 6.3 编辑

- 点击账单行的编辑入口，打开与新增账单相同的确认表单。
- 用户可以修改金额、收支、分类、备注和日期。
- 保存编辑结果时更新原账单，不新建一笔重复账。
- 编辑成功后，列表、首页最近账单和首页汇总立即按新值更新；取消编辑则原账单保持不变。

### 6.4 删除

- 删除必须先二次确认，并明确显示将被删除的账单摘要。
- 删除成功后从列表和首页汇总中移除。
- 删除后在当前页面提供撤销入口；撤销成功恢复原账单及其汇总。
- V1 不建立回收站、批量删除或跨设备恢复能力。

## 7. 首页

### 7.1 必须包含的内容

首页按使用频率排列以下内容：

1. 快速记账入口，用户进入后可以直接输入一句话。
2. 今天支出：所有日期为今天且收支为支出的账单金额合计。
3. 本月支出：当前本地月份内所有支出金额合计。
4. 本月收入：当前本地月份内所有收入金额合计。
5. 最近账单：展示最近保存的账单，默认显示最近 5 笔，并能进入完整列表。

### 7.2 不需要的其他内容

V1 首页不增加余额、预算提醒、趋势图、分类占比、消费建议、广告、账户信息或其他仪表盘内容。首页只服务于快速记账、查看三个基础汇总和回看最近账单。

### 7.3 汇总口径

- 金额按已保存账单计算，待确认内容不计入汇总。
- 支出只计入支出账单，收入只计入收入账单，不用正负号混合推断。
- 修改或删除账单后，相关汇总必须重新反映当前已保存数据。
- 没有数据时各金额显示为 0，并保持页面可继续快速记账。

## 8. V1 分类列表

### 8.1 分类来源与重复整理

V1 分类以用户给出的基础分类清单为准，只做必要整理，不为了样例少而删除基础分类。相同语义的词归并为一个最终分类：

| 用户给出的分类或样例词 | 是否重复或需要归并 | 最终处理 |
| --- | --- | --- |
| 餐饮、吃面、午饭 | 吃面和午饭都是餐饮子场景 | 保留“餐饮” |
| 买菜 / 食品 | 买菜和食品高度重合，不拆成两个分类 | 保留“买菜/食品” |
| 交通、打车 | 打车、公交、地铁等日常出行归入交通 | 保留“交通” |
| 车辆 / 加油 | 加油、停车、洗车等车主场景与普通交通不同 | 保留“车辆/加油” |
| 工资 / 收入 | “收入”是收支方向，不适合作为唯一分类名 | 保留“工资”，另设“其他收入” |
| 其他 | 收入和支出的其他项需要分开，避免统计混乱 | 拆成“其他支出”和“其他收入” |
| 日用品、居住、通讯、娱乐、孩子、医疗 | 都是常见个人记账场景，不明显重复 | 全部保留 |

### 8.2 最终分类

收入分类：

- 工资
- 其他收入

支出分类：

- 餐饮
- 买菜/食品
- 日用品
- 交通
- 车辆/加油
- 居住
- 通讯
- 娱乐
- 孩子
- 医疗
- 其他支出

“其他支出”和“其他收入”是无法分类时的明确兜底选项。V1 不允许用户自定义分类，不再继续拆分“吃面”“午饭”“打车”等更细子分类；“加油”单独归入“车辆/加油”。

## 9. 异常情况规则

| 情况 | 系统行为 | 用户结果 |
| --- | --- | --- |
| 空输入 | 不执行识别，不生成账单；提示用户输入一句记账描述。 | 用户补充输入或取消。 |
| 无金额 | 保留原句，提示未识别金额；不以 0 或默认金额代替。 | 用户补充一个金额后重新识别，或在确认页修正。 |
| 只有金额 | 先展示已识别金额；收支方向和分类保持待确定。 | 用户必须选择收支方向和分类后才能保存，系统不默认支出。 |
| 两个金额 | 标记为多金额歧义；V1 不自动拆成两笔，也不静默选择第一个或最后一个。 | 用户返回改写为一笔，或手动把金额改为一个明确值后再保存。 |
| 无法分类 | 若收支方向已知，建议“其他支出”或“其他收入”，并标记待确认。 | 用户必须确认兜底分类或改选已有分类后保存。 |
| 无法判断收入/支出 | 不猜测方向，不把所有未知内容默认为支出。 | 用户在确认页选择收入或支出后继续；未选择时不能保存。 |
| 连续保存相同账 | 若当前账与刚刚保存的上一笔在日期、金额、收支、分类、备注上完全相同，显示重复提醒。 | 用户可以返回修改，也可以明确选择仍然保存；提醒不应阻止真实的重复消费。 |
| 误删 | 删除前二次确认，删除后立即提供撤销入口。 | 用户在撤销入口有效期间可以恢复原账；撤销成功后重新计入列表和汇总。 |
| 修改已保存账 | 编辑使用同一套字段校验；保存时更新原账，不产生新账。 | 用户看到修改后的列表和汇总；取消则不改变原账。 |
| 负数金额 | 将负数视为非法输入，不自动取绝对值，不自动翻转收支方向。 | 用户改成正数并选择正确的收入或支出；未修正时不能保存。 |

- 支付宝自动读取。
- 淘宝同步。
- 银行同步。
- 通知读取。
- OCR。
- 截图识别。
- CSV/Excel 账单导入。
- 登录。
- 注册。
- 多用户。
- 云同步。
- 好友。
- 社交。
- AI 聊天。
- 高级预算。
- 复杂报表。
- 投资。
- 贷款。

- 独立支付来源字段。

## 11. 产品验收标准与停止线

### 11.1 V1 完成标准

只有下列条件全部满足，才算 V1 完成：

- 用户可以从首页快速入口输入一句话，进入识别结果和确认页面。
- 八个规定样例能给出本文第 3 节所列的默认金额、收支、分类、备注和日期建议。
- 用户可以在确认页修改五个账单字段；修改后的值才是保存值。
- 必填字段缺失、金额非法或歧义未处理时，无法保存且有可理解的提示。
- 保存后的账单立即出现在账单列表，列表行展示五个规定字段。
- 用户可以查看、编辑和删除已保存账单；编辑不重复创建，删除有确认和撤销。
- 今天支出、本月支出、本月收入会根据已保存、已修改、已删除的账单得到正确结果。
- 无账单时首页和账单列表都有清晰空状态，仍可快速记账。
- 规则、关键词、兜底分类和异常行为与本文一致，并且不需要云端大模型才能完成闭环。
- 数据在本地保存，重新打开本地 Web App 后仍可查看；不引入账号、外部平台或同步依赖。
- 第 10 节列出的不做项没有被实现或隐藏接入。

### 11.2 停止线

达到 11.1 的全部条件后，V1 产品工作停止。不得为了“更智能”“更完整”继续加入导入、同步、识别渠道、预算、报表、账号、社交或其他未批准能力。后续问题应先记录为缺陷、产品澄清或下一阶段候选，不得直接改变 V1 范围。

## 12. 给后续 Agent 的使用说明

本文是后续工作的产品真相来源。后续 Agent 可以补充测试、设计或实现说明，但不能悄悄改变字段、分类、流程或非目标；发现冲突时应回报主 Agent，由主 Agent 决定是否修改本文。

### Research Agent

- 只研究个人新手对“一句话记账”的理解、常见表达和容易混淆的词。
- 输出应服务于规则词表、提示语和样例覆盖，不得借研究结果加入导入、同步、账号或聊天能力。
- 研究发现与本文冲突时，报告冲突和证据，不直接改产品范围。

### Data Agent

- 按五个账单字段和最终分类准备本地测试数据、日期边界和汇总口径。
- 验证今天、本月、修改、删除对三个首页指标的影响。
- 不增加商户、来源、用户、同步状态等字段，不引入外部数据源。

### Classification Agent

- 把第 3 节样例、第 8 节分类和第 9 节异常规则整理成可测试的关键词及冲突表。
- 优先保持可解释和可修改；无法判断时使用确认页或兜底分类，不擅自猜测。
- 不引入云端模型，不拆分 V1 分类，不把收入/支出方向当成分类。

### UX Agent

- 设计输入、识别、确认、保存、列表、编辑、删除和撤销删除的完整状态流。
- 必须覆盖空输入、缺金额、多金额、待确认分类、方向不明、负数、重复保存和误删。
- 不增加额外首页模块、筛选、报表或复杂设置。

### UI Agent

- 依据本文规定的页面内容和字段状态形成清晰、适合新手扫描的界面。
- 重点保证金额、收支、分类、备注、日期以及保存和删除反馈不被混淆。
- 不制作营销页，不用视觉包装掩盖未完成状态，不加入禁用能力入口。

### Frontend Agent

- 只实现本文允许的输入、识别确认、保存、列表、编辑、删除、撤销和首页汇总交互。
- 以本文的异常规则和验收标准作为行为基线，不能把识别结果直接当最终数据。
- 在产品范围未更新前，不添加外部平台连接、登录、导入、图表或聊天。

### Backend Agent

- 只负责本地账单持久化、单笔 CRUD、字段校验和首页三个汇总所需的能力。
- 以五个字段、正数金额、单笔输入和最终分类为数据约束；编辑必须更新原账。
- 使用本地 SQLite 约束，不增加认证、云同步、外部采集或支付平台接口。

### Test Agent

- 覆盖八个规定样例、全部异常情况、确认页修改、保存、列表查看、编辑、删除撤销和首页汇总。
- 同时验证空数据状态、同日排序、连续重复提醒、负数拒绝和数据重开后仍可查看。
- 增加范围回归检查，确认禁用能力没有入口、调用或隐式依赖。

### Review Agent

- 以本文逐项核对产品行为、字段、分类、错误处理、数据边界和停止线。
- 先报告会造成错误记账、数据丢失、范围越界或验收失败的问题，再报告一般体验问题。
- 不以“未来可能有用”为理由扩展 V1；所有范围争议回到主 Agent 和本文。

## 13. 仍需主 Agent 确认的问题

本文已给出可执行的 V1 基线，但以下三项是基于当前样例做出的暂定决策，建议主 Agent 在开始设计或编码前一次性确认：

1. 默认备注是否采用本文规则，即保留去除金额、日期和明显收支词后的描述性文字；如果不采用，需要明确是保留完整原句还是默认留空。
2. “连续保存相同账”的重复提醒触发范围，以及删除后的撤销入口有效时长。本文当前按上一笔完全相同字段提醒、删除后立即可撤销作为基线。

若主 Agent 未提出调整，则本文中的暂定决策可作为 V1 实施和验收依据。除上述确认项外，不应再为 V1 增加新的产品问题或功能范围。
